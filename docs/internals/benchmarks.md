# Benchmark Results

Performance analysis of Mirror Bridge compared to pybind11, nanobind, and
SWIG. The runtime table below is **regenerated by CI** (`benchmarks.yml`) so
it always reflects the current code; compile-time numbers are from the
checked-in benchmark scripts.

## Summary

- **Runtime**: ~3-4x faster than pybind11 on call-heavy operations, parity
  with nanobind on dispatch, faster on object construction
- **Compile time**: comparable to nanobind once a precompiled header is used
- **Binding code**: zero lines regardless of project size (auto-discovery)

**Read the ratios as bounds, not as the binding layer.** Every number above is timed as `benchmark(name, lambda: ..., n)`, so each one carries a Python loop iteration and a full Python function call on top of the operation. On this run that floor is **24.1 ns** for an empty lambda and **35.2 ns** for the cheapest real C method call CPython can make. The constant is the same for all four frameworks, so it does not cancel in a ratio: it pulls every ratio toward 1.00. A ratio above 1.00x is therefore a **lower** bound on how much faster mirror_bridge's binding layer is, and a ratio below 1.00x understates the gap the other way. A row within a few percent of 1.00 is not a tie that has been measured; it is a difference this instrument cannot resolve.

## Trading Workloads

_Regenerated at commit `5c59d278124d15a390e9923dc6a3108815c582e0` on GitHub Actions ubuntu-latest (4 cores, containerized)._

Three trading workloads, chosen so the answer to "does my binding framework matter" falls out of the data. Every framework binds the [same header](../../benchmarks/runtime/shared/trading_bench.hpp) and every batched method delegates to the same kernel the per-element method uses, so no framework is measured against a different implementation. Each framework is timed in its own interpreter, fastest of nine runs with the collector off. Reproduce with `./run_benchmarks.sh`.

### Order book — one crossing per market event

A price-level book on a 4096-tick ladder, 20,000 events, **60% add / 30% cancel / 10% market**. Branchy pointer chasing with nothing to vectorise, so numpy is not a competitor and the binding layer is the whole story. The book matches against price levels rather than individual resting orders.

| | ns/event, one call per event | ns/event, whole stream in one call |
|---|---:|---:|
| python | 145 | - |
| pybind11 | 144 | 46.4 |
| mirror_bridge | 81.0 | 12.5 |
| nanobind | 86.4 | 13.1 |

At one crossing per event the fastest binding buys only 1.8x over pure Python (81.0 vs 145 ns): the crossing costs most of what the C++ saves. Batching the same work into one call is what changes the picture — 12.5 ns/event for mirror_bridge, 11.6x pure Python and 6.5x the same binding called per event.

### Black-Scholes — compute-heavy

20,000 contracts per call. The normal CDF is the Abramowitz & Stegun polynomial rather than `std::erf`, so Python, numpy and C++ evaluate the identical expression and the columns differ in substrate, not arithmetic. "scalar out" returns one double instead of a vector, isolating the cost of handing the results back.

| | ns/contract | scalar out |
|---|---:|---:|
| python | 777 | - |
| numpy | 52.0 | - |
| pybind11 | 76.4 | 69.8 |
| mirror_bridge | 34.3 | 33.2 |
| nanobind | 42.1 | 35.5 |

Arithmetic dominates, so the binders bunch up: mirror_bridge is 1.52x numpy, and every binder is 10x to 23x pure Python. This is the half of a trading stack where the binding layer does not matter.

### Crossing frequency — how much batching buys

One EWMA-crossover recurrence over 262,144 ticks at every chunk size; `on_batch` is a loop over `on_tick`, so the arithmetic is byte-identical and the only thing that changes is how often Python is entered. numpy+scipy appears at the full-array size, where `signal.lfilter` can actually be used — an EWMA is a linear recurrence, so a vectorised filter is the honest baseline rather than a Python loop over numpy scalars.

| ticks per call | python | numpy+scipy | pybind11 | mirror_bridge | nanobind |
|---:|---:|---:|---:|---:|---:|
| 1 | 287 | - | 67.4 | 26.6 | 27.4 |
| 8 | 96.0 | - | 23.6 | 6.8 | 7.5 |
| 64 | 75.7 | - | 12.6 | 4.0 | 4.6 |
| 512 | 72.6 | - | 11.3 | 3.4 | 3.9 |
| 4,096 | 73.9 | - | 10.9 | 3.6 | 4.0 |
| 32,768 | 73.1 | - | 10.4 | 3.4 | 3.7 |
| 262,144 | 72.7 | 21.7 | 10.6 | 3.5 | 3.9 |

Batching is worth 6x to 8x per framework, and almost all of it has arrived by 64 ticks per call. What does NOT happen is the frameworks converging: the spread between them is 2.5x at one tick per call and 3.0x at 262,144, because once the per-call overhead is amortised away what is left is converting the input, and that cost is per element. The next table separates the two.

### Getting the numbers in — the flat tail explained

The whole 262,144-tick array in one call, handed over two ways: as a Python `list`, and as an `array.array('d')`, which is a contiguous buffer. Same kernel, same work, so the difference is purely how each framework ingests it.

| | list | array.array('d') |
|---|---:|---:|
| pybind11 | 10.6 | 13.0 |
| mirror_bridge | 3.4 | 2.9 |
| nanobind | 3.8 | 10.2 |

mirror_bridge recognises the buffer and memcpys it: 1.2x faster, with nothing asked of the author. pybind11 and nanobind get *slower*, because their `stl.h` casters walk it through the generic sequence protocol. That is a real advantage but a narrow one, and it is worth being precise about: both can match or beat this if the author hand-writes a `py::array_t` / `nb::ndarray` signature. The claim is parity-or-better for zero code, not that the ceiling is higher.

### Where mirror_bridge loses

- Nothing in this run, counting only gaps wider than the 128.5% the identical baselines moved between processes.

What is defensible is the combination, not the speed alone: hand-written binding lines for these three classes are mirror_bridge 9, nanobind 27, pybind11 29. The mirror_bridge figure is the `MIRROR_BRIDGE_MODULE` block; through the CLI it is zero.

## Compile-Time Performance

### Without Precompiled Headers

| Project Size | Mirror Bridge | pybind11 | nanobind |
|--------------|--------------|----------|----------|
| Simple (1 class) | 567ms | 1,938ms | 165ms |
| Medium (10 classes) | 1,580ms | 3,637ms | 218ms |

### With Precompiled Headers

| Project Size | Mirror Bridge + PCH | nanobind + stub |
|--------------|---------------------|-----------------|
| Simple (1 class) | **194ms** | 165ms |
| Medium (10 classes) | **252ms** | 218ms |
| PCH Build (one-time) | 600ms | 800ms |

**Key insight**: with PCH, Mirror Bridge achieves comparable compile times to
nanobind while requiring zero binding code.

## Why Is Mirror Bridge Fast?

### Compile-Time

1. **Reflection eliminates template metaprogramming overhead**
   - Direct member enumeration via `std::meta::members_of()`
   - No recursive template instantiation

2. **PCH amortizes parsing cost**
   - Parse `<meta>`, `<Python.h>`, Mirror Bridge once
   - Reuse across all compilation units

### Runtime

1. **Direct Python C API calls**
   - No intermediate abstraction layers
   - Function pointers stored directly in PyMethodDef

2. **Zero dispatch overhead**
   - Type information resolved at compile-time; reflection splice calls
     (`(obj.[:member_fn:])(...)`) are visible to the inliner, unlike opaque
     member-function-pointer dispatch

3. **Minimal wrapper objects**
   - PyWrapper<T> contains only essential fields
   - Direct pointer to C++ object

## Methodology

- Every framework binds the same C++ class (`benchmarks/runtime/shared/benchmark_class.hpp`)
- Same compiler for all frameworks, `-O3 -DNDEBUG`; only the binding layer differs
- 5 runs per measurement, median reported, warmup pass first
- Compare ratios, not absolute times: ratios are stable across machines

## Measured and declined

Things that look like they should pay and do not. Each was built far enough to
measure, and the measurement is recorded here so it does not have to be
re-litigated.

### `tp_vectorcall` on the bound type

CPython's specializing interpreter (3.11+) only emits `CALL_BUILTIN_CLASS` for
a type that has a `tp_vectorcall` slot. Our generated types do not set one, so
every construction stays on the generic `CALL` path. Confirmed with
`dis.get_instructions(f, adaptive=True)` on 3.13: a type without the slot keeps
`CALL`, and the same type with it specializes.

Two types identical but for the slot, 1.5M constructions, best of seven:

| | `tp_init` only | with `tp_vectorcall` | |
|---|---|---|---|
| 3.13, no arguments | 27.0 ns | 25.2 ns | 1.07x |
| 3.13, three arguments | 29.7 ns | 28.1 ns | 1.06x |
| 3.10, no arguments | 46.2 ns | 45.7 ns | 1.01x |
| 3.10, three arguments | 48.4 ns | 50.0 ns | 0.97x |

So it is worth 6-7% on 3.11+ and nothing before it, because the argument tuple
it avoids costs about 2 ns from the tuple freelist, not the 20 ns it looks like
it should.

The cheap way to get it is also the wrong way. A slot that converts the
arguments back into a tuple and dict and hands them to `type_call` keeps
constructor resolution in one place, but it is **slower than having no slot at
all** — 0.90x at no arguments and 0.73x at three on 3.13 — because it pays for
a tuple that CPython's own fallback builds more cheaply. The only version that
wins is one that resolves constructors directly from the vectorcall array,
which means a second implementation of overload resolution with defaults,
keywords and trampolines in it. Six percent is not worth two copies of that:
every binding bug found in this codebase so far has come from one piece of
logic having two implementations.

Worth revisiting if construction ever dominates a real workload, or if
constructor resolution is restructured for another reason and the flat-array
shape falls out of it for free.

## Trade-offs

**Advantages**: zero binding code, faster than pybind11 at runtime,
automatic binding updates when classes change, multi-language from a single
codebase.

**Considerations**: requires the clang-p2996 reflection compiler (Docker),
PCH needed for competitive compile times, nanobind matches mirror_bridge on
raw dispatch speed (its weakness is the hand-written binding code, not
performance).
