# Benchmark Results

Performance analysis of Mirror Bridge compared to pybind11, nanobind, and
SWIG. The runtime table below is **regenerated by CI** (`benchmarks.yml`) so
it always reflects the current code; compile-time numbers are from the
checked-in benchmark scripts.

## Summary

- **Runtime**: ~3-4x faster than pybind11 on call-heavy operations, parity
  with nanobind on dispatch, faster on object construction
- **Compile time**: comparable to nanobind once a precompiled header is used
- **Binding code**: zero lines regardless of project size (auto-discovery)

## Trading Workloads

Three trading workloads, chosen so the answer to "does my binding framework matter" falls out of the data. Every framework binds the [same header](../../benchmarks/runtime/shared/trading_bench.hpp) and every batched method delegates to the same kernel the per-element method uses, so no framework is measured against a different implementation. Reproduce with `./run_benchmarks.sh`.

### Order book — one crossing per market event

A price-level book on a 4096-tick ladder, 20,000 events, **60% add / 30% cancel / 10% market**. Branchy pointer chasing with nothing to vectorise, so numpy is not a competitor and the binding layer is the whole story. The book matches against price levels rather than individual resting orders.

| | ns/event, one call per event | ns/event, whole stream in one call |
|---|---:|---:|
| python | 136 | - |
| pybind11 | 140 | 62.5 |
| mirror_bridge | 93.8 | 17.6 |
| nanobind | 84.7 | 11.6 |

At one crossing per event **pybind11 is slower than pure Python** (140 vs 136 ns): the binding overhead exceeds what the C++ saves. Batching the same work into one call is what changes the picture — 17.6 ns/event for mirror_bridge, 7.7x pure Python.

### Black-Scholes — compute-heavy

20,000 contracts per call. The normal CDF is the Abramowitz & Stegun polynomial rather than `std::erf`, so Python, numpy and C++ evaluate the identical expression and the columns differ in substrate, not arithmetic. "scalar out" returns one double instead of a vector, isolating the cost of handing the results back.

| | ns/contract | scalar out |
|---|---:|---:|
| python | 809 | - |
| numpy | 30.6 | - |
| pybind11 | 67.7 | 61.5 |
| mirror_bridge | 26.4 | 26.5 |
| nanobind | 29.4 | 23.9 |

Arithmetic dominates, so the binders bunch up: mirror_bridge is 1.16x numpy, and pure Python is 31x slower than any of them. This is the half of a trading stack where the binding layer does not matter.

### Crossing frequency — how much batching buys

One EWMA-crossover recurrence over 262,144 ticks at every chunk size; `on_batch` is a loop over `on_tick`, so the arithmetic is byte-identical and the only thing that changes is how often Python is entered. numpy+scipy appears at the full-array size, where `signal.lfilter` can actually be used — an EWMA is a linear recurrence, so a vectorised filter is the honest baseline rather than a Python loop over numpy scalars.

| ticks per call | python | numpy+scipy | pybind11 | mirror_bridge | nanobind |
|---:|---:|---:|---:|---:|---:|
| 1 | 235 | - | 68.7 | 29.5 | 22.3 |
| 8 | 98.0 | - | 30.7 | 9.7 | 7.3 |
| 64 | 76.9 | - | 14.4 | 5.4 | 4.6 |
| 512 | 73.7 | - | 12.3 | 4.6 | 4.3 |
| 4,096 | 73.6 | - | 11.9 | 4.7 | 4.2 |
| 32,768 | 73.0 | - | 11.8 | 4.7 | 4.2 |
| 262,144 | 73.0 | 12.9 | 11.9 | 4.7 | 4.4 |

Batching is worth 5x to 6x per framework, and almost all of it has arrived by 64 ticks per call. What does NOT happen is the frameworks converging: the spread between them is 3.1x at one tick per call and 2.7x at 262,144, because once the per-call overhead is amortised away what is left is converting the input, and that cost is per element. The next table separates the two.

### Getting the numbers in — the flat tail explained

The whole 262,144-tick array in one call, handed over two ways: as a Python `list`, and as an `array.array('d')`, which is a contiguous buffer. Same kernel, same work, so the difference is purely how each framework ingests it.

| | list | array.array('d') |
|---|---:|---:|
| pybind11 | 11.9 | 17.2 |
| mirror_bridge | 4.6 | 2.4 |
| nanobind | 4.3 | 10.5 |

mirror_bridge recognises the buffer and memcpys it: 1.9x faster, with nothing asked of the author. pybind11 and nanobind get *slower*, because their `stl.h` casters walk it through the generic sequence protocol. That is a real advantage but a narrow one, and it is worth being precise about: both can match or beat this if the author hand-writes a `py::array_t` / `nb::ndarray` signature. The claim is parity-or-better for zero code, not that the ceiling is higher.

### Where mirror_bridge loses

- **nanobind** is faster on order book, per event: 84.7 vs 93.8 ns/event (1.11x).
- **nanobind** is faster at every point of the crossing-frequency sweep, by up to 1.34x.

What is defensible is the combination, not the speed alone: hand-written binding lines for these three classes are mirror_bridge 9, nanobind 27, pybind11 29. The mirror_bridge figure is the `MIRROR_BRIDGE_MODULE` block; through the CLI it is zero.

## Compile-Time Performance

### Without Precompiled Headers

| Project Size | Mirror Bridge | pybind11 | nanobind |
|--------------|--------------|----------|----------|
| Simple (1 class) | 567ms | 1,938ms | 165ms |
| Medium (10 classes) | 1,580ms | 3,637ms | 218ms |

### With Precompiled Headers

| Project Size | Mirror Bridge + PCH | nanobind + stub |
|--------------|---------------------|-----------------|
| Simple (1 class) | **194ms** | 165ms |
| Medium (10 classes) | **252ms** | 218ms |
| PCH Build (one-time) | 600ms | 800ms |

**Key insight**: with PCH, Mirror Bridge achieves comparable compile times to
nanobind while requiring zero binding code.

## Developer Experience

### Lines of Binding Code Required

| Task | Mirror Bridge | pybind11 | nanobind |
|------|--------------|----------|----------|
| 1 class, 5 members | 0 | 18 | 15 |
| 10 classes | 0 | 180 | 150 |
| 50 classes | 0 | 900 | 750 |

With auto-discovery, the binding-code count stays at zero regardless of
project size; regenerating after a header change is one CLI invocation.

## Why Is Mirror Bridge Fast?

### Compile-Time

1. **Reflection eliminates template metaprogramming overhead**
   - Direct member enumeration via `std::meta::members_of()`
   - No recursive template instantiation

2. **PCH amortizes parsing cost**
   - Parse `<meta>`, `<Python.h>`, Mirror Bridge once
   - Reuse across all compilation units

### Runtime

1. **Direct Python C API calls**
   - No intermediate abstraction layers
   - Function pointers stored directly in PyMethodDef

2. **Zero dispatch overhead**
   - Type information resolved at compile-time; reflection splice calls
     (`(obj.[:member_fn:])(...)`) are visible to the inliner, unlike opaque
     member-function-pointer dispatch

3. **Minimal wrapper objects**
   - PyWrapper<T> contains only essential fields
   - Direct pointer to C++ object

## Methodology

- Every framework binds the same C++ class (`benchmarks/runtime/shared/benchmark_class.hpp`)
- Same compiler for all frameworks, `-O3 -DNDEBUG`; only the binding layer differs
- 5 runs per measurement, median reported, warmup pass first
- Compare ratios, not absolute times: ratios are stable across machines

## Trade-offs

**Advantages**: zero binding code, faster than pybind11 at runtime,
automatic binding updates when classes change, multi-language from a single
codebase.

**Considerations**: requires the clang-p2996 reflection compiler (Docker),
PCH needed for competitive compile times, nanobind matches mirror_bridge on
raw dispatch speed (its weakness is the hand-written binding code, not
performance).
