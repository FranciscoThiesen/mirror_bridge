## [Unreleased]

### Added
- **The C# backend reaches the other backends, and passes two of them.** It began as scalars, bool and strings. It now also carries enums as real C# enums over the same underlying type, method overloading (one exported symbol per overload, with C#'s own resolution picking, refusing only the pair C# genuinely cannot distinguish), static methods, constructors of any arity, inherited data members and methods, nested objects, and `std::vector<T>` of a scalar or string. A class-typed **member** is a view of the real subobject so writes reach the owning object, while one **returned by value** is a copy the caller owns, because a pointer to the temporary would dangle; the same split governs vectors, so `obj.samples.Add(x)` reaches the C++ vector and `obj.history()` hands back a copy. The view holds a strong reference to its owner, which is what stops the GC collecting the owner first, and that reference is read through `GC.KeepAlive` rather than merely stored, because a field written and never read is `CS0414` and an error in any project built with warnings-as-errors. The generated vector view implements `IReadOnlyList<T>` so LINQ works on it, and reads `Count` from C++ on every access rather than caching it. Inherited data members needed a new walk: `nonstatic_data_members_of` reports only direct members, so `core` gained `data_members_with_bases` beside the member-function cache that already walked `bases_of` for exactly the same reason. Two rows now read better for C# than for Lua and JavaScript, and not by accident of the table: Lua reaches only the first overload of a name and JavaScript only the last, neither says so, and both pass an enum as a bare integer with no enum type at all.
- **The generated C# is what a .NET engineer would accept, which took finding three things that were wrong.** A review of the real generated output, compiled with `mcs` and run under `mono`, found that the wrapper could be finalized mid-call: with an `IntPtr` field the last read of the instance is inside the argument list, so the JIT may report it dead and the finalizer may run `Delete` while the native call is still on the stack. Every class now wraps a `SafeHandle`, which the runtime ref-counts across the call and which makes `Dispose` idempotent and thread-safe besides. Second, a C++ name that collides with the generated surface produced C# that does not compile — `int Handle` and a method called `Dispose()` are house style at several large shops — and there is a second, independent collision the native ledger cannot see, because a C# property `X` compiles to hidden `get_X`/`set_X` and so a method `get_x` beside a member `x` is "already reserved". Both are resolved by renaming with a trailing underscore, reported in the run output and written into the generated class. Third, the library was named `lib<module>.so` on every platform, which `DllImport` probing can never find on macOS; it is now `.dylib` on Darwin and `<module>.dll` on Windows. Smaller things from the same review: the exception kind is carried across the boundary through a `dynamic_cast` ladder so a caller can catch `ArgumentException` for `std::invalid_argument` instead of one `InvalidOperationException` for everything; `mb_*_delete` catches, which the shim's own comment already claimed every entry point did; a failed string allocation records an error instead of arriving as a successful empty string; `ExactSpelling = true` stops the runtime probing a second, non-existent name; parameter names are the real C++ ones rather than `a0`, `a1`, which this project's Python stubs have carried all along; and the generated file compiles under `-warnaserror` with no warnings.
- **One P/Invoke transition per call instead of two.** The generated code asked the library whether an error was pending after every call, which is itself a transition. The error slot's address is now cached per managed thread and tested with `Marshal.ReadInt32`. Measured 58.1 to 49.2 ns/call under mono, which is 1.18x rather than the 2x it looks like, because the second transition carried no arguments.
- **The CLI reads a project's `compile_commands.json` instead of asking for its build configuration again.** The argument for this is written in the compatibility corpus' own manifest: opencv needs a hand-generated `opencv_modules.hpp` written into its checkout before its headers parse, open3d is reachable only for `geometry/` because `core/` wants MKL and `ml/` wants CUDA, eigen needs sixteen `--exclude` patterns, abseil needs a bespoke build command. Every one of those is a person rediscovering, as `-I` and `-D` flags, something the project's own build system already recorded. At a few hundred thousand lines that is a chore; at twenty million it is the entire job, and it is the reason pointing a generator at a large codebase fails for a dull reason rather than an interesting one. `--compile-commands PATH` harvests the include paths and defines by allowlist — `-I`, `-isystem`, `-iquote`, `-idirafter`, `-iframework`, `-F`, `-D`, `-U`, `-include` — because an unrecognised flag in a large project's build is far likelier to be an optimisation, a sanitiser or a dependency-generation flag than something the reflection pass needs, and taking it on faith is how a generator ends up passing `-flto` to a syntax-only probe. The flags reach both compile sites the script has, for the same reason the existing `-D` handling does: a discovery unit preprocessed differently from the module reports a different library from the one that gets built. Three deliberate decisions. The project's own `-std=` is **dropped**, because reflection needs C++26 and the project is on something older, so its standard flag winning would break the pass outright; that is reported rather than silent. MSVC and clang-cl spellings — `/I`, `/D`, `/U`, `/external:I`, `/FI` — are translated, which is not politeness but the point: MSVC has no reflection support, so a Windows project's build runs there while generation runs on a machine that has a reflection compiler, and the database handed over is full of MSVC flags. And a flag carrying whitespace is **refused with a warning** rather than passed, because the CLI interpolates these into a string that word-splits, so one `-D` with a spaced value would silently become two flags and change what the compiler was told. A macro defined two ways across one build is reported the same way instead of being resolved quietly. `--compile-commands-for PATH` scopes the database to a subtree, because on a monorepo the union of every subsystem's flags is both enormous and self-contradictory, and `--replace-prefix OLD=NEW` maps a database written on one machine onto the paths of another. That last flag exists because of what the tests found: `os.path.isabs("C:/proj/inc")` is **false** on POSIX, so every Windows path was being joined onto the entry's build directory, producing `-I/linux/build/C:/proj/inc` — an include path that can match nothing and reports no error. That is the normal case for this feature, not an edge case.
- **`--discover-only` answers "can this codebase be read at all" without building a module per class.** Reading a large project's headers is the expensive and interesting half of the work; generating and compiling a module for everything found is what turns minutes into hours, and the corpus records 138 seconds for Open3D's geometry subtree alone. `--discover-only` stops after discovery and reports the class count, the enum count, the header count, the seconds the reflection pass took, and the harvested-flag count. The field that matters is `source`: `reflection` means the headers were read after the preprocessor and the class list is real, while `text scan` means the reflection unit failed and every name came from reading header text, which cannot see a class declared through an export macro (`class MYLIB_API Widget`) or resolve a typedef. A large codebase reporting `text scan` is not a slow problem, it is a blocked one, and generating from that list would bind the wrong names — so the report says that outright and names the planner log that explains the failure. Pairs with `--json`, which emits one object carrying the counts, the class and enum names, the headers and the compile-database report.
- **A C# backend (`--lang csharp`).** C# reaches native code through P/Invoke, so unlike CPython, Lua and Node there is no host C API a generated translation unit can call: the binding needs a flat C ABI on one side and C# declarations on the other, which is the same shape SWIG's C# module has and for the same reason. The architecture is forced further by a hard limit in P2996 — **reflection cannot declare a function whose name is computed**, and every P/Invoke target needs its own exported symbol — so a generator built with reflection emits the shim as text and an ordinary compile turns that into the shared library. The alternative, one indexed entry point dispatching on a class id, would have cost a jump table on every call, and the point of this project is that the generated path is the code a person would have written. Emitting text turned out to be the right shape for the people who want this most: **the shim contains no reflection at all**, so it rebuilds with whatever compiler they already have, and for anyone on MSVC a shim that needed reflection would have been unusable. Both files come out of one reflection pass over one class list, so a member renamed in C++ renames the exported symbol and the C# property together — there is no second list to keep in step. What crosses today: a default constructor, arithmetic members and parameters, `bool` (as a 32-bit integer on the wire, converted at the edge, because a C++ `bool` is one byte and C# marshals one as four and the mismatch is silent), `std::string` (a UTF-8 heap copy out with an explicit free, `LPUTF8Str` marshalled in, rather than a pointer into the live `std::string` that would dangle the moment anything mutated the object), methods over those types, and `const` members as read-only properties. Generated classes are `IDisposable` with a finalizer. A C++ exception is caught at every entry point and recorded in a thread-local, then raised on the managed side as an exception carrying `what()`, because an exception crossing `extern "C"` is undefined behaviour. Everything that cannot cross yet — a container member, a class-typed return, a second overload of a name — is named in the run output **and** as a comment in the generated C# at the point where the member would have been, because a generator that silently binds a subset leaves the caller unable to tell a missing member from an absent one. Generated code for both files is indented by one brace-depth formatter rather than by the care taken at each emission site; the first version had three different indentations inside a single class because each site had guessed separately.
### Changed
- **A `std::vector` data member is a live view of the C++ vector, not a copy.** `obj.items.append(9)` and `obj.items[0] = 9` were both accepted and both silently discarded: the getter built a fresh `array.array` or `list` on every read, the mutation landed on that temporary, and the temporary was dropped at the end of the statement. No exception, no warning, no way to find out. This is the container half of what member views did for class members in PR #32, and it rests on the same fact: a non-static data member is interior to the wrapped object by construction, so the getter can hand back something that borrows the storage and keeps its owner alive, which a method return cannot. The view registers as a `collections.abc.MutableSequence` and supports `len`, indexing, negative indices, iteration, `in`, `==` against any sequence, `append`, `extend`, `insert`, `pop`, `clear`, `del` and `tolist()`. A numeric one also exports the buffer protocol, so `numpy.asarray(obj.xs)` shares the vector's own storage. Not copying also removes an O(n) allocation from every attribute read: measured on a `vector<double>` member, 122 ns to 44 ns at ten elements and 54.0 us to 44 ns at a hundred thousand, where the new cost is flat because it no longer depends on the length. Three cases keep the copy on purpose — a method return, because interiority cannot be established for one; a `const` member, because a writable view would get around what C++ said; and `std::vector<bool>`, which packs its elements and has no element to reference. Resizing is refused with `BufferError` while a `memoryview` or numpy array is outstanding, since it would reallocate the storage they point at; the export count is kept per C++ container rather than per view object, because every attribute read builds a new view of the same vector and a per-view count said yes to exactly the append that invalidates the buffer. **Migration:** code that asserted `isinstance(obj.field, list)` or `isinstance(obj.field, array.array)`, or that passed a member straight to `json.dumps`, wants `list(obj.field)`. This changes a mapping [stability.md](docs/reference/stability.md) lists as stable, which is why it is called out here rather than filed under Fixed.

### Fixed
- **Lua and JavaScript could not bind any class with a `const` data member, or with a member whose type has no default constructor.** Both setters declare a local of the member's declared type to convert into and then move into place. For a `const` member that local is a default-initialised const and the assignment a write to a const lvalue; for a type like `nlohmann::detail::dtoa_impl::diyfp`, which declares only `diyfp(uint64_t, int)`, there is no default constructor to declare it with. Either one is ill-formed, so the whole module failed to compile rather than that one attribute failing to assign — and the Python backend has handled both for long enough that `tests/const_members/` documents them in comments. It had only a Python test, which is exactly why nobody saw it. Both setters now refuse such a member by name at runtime, and JavaScript's constructor path had the same shape twice over in two unguarded `new T()` calls, so a class with no default constructor took the module down from there as well. `tests/lua/const_members/` and `tests/js/const_members/` were added, because the gap was never in the code so much as in which languages the test covered. Found while bringing the C# backend to parity: C# had to decide what a const member means, and the answer turned out to be one the other two had never been asked.
- **Reflection was silently losing to a text scan on industrial codebases, over one constant.** Discovery walks every class in the codebase at compile time, which makes it the pass most likely to exhaust the compiler's constexpr evaluation limit, and the cost of exhausting it is not a slow build but a wrong answer: the CLI falls back to scanning header text, which cannot see a class declared through an export macro and reports the macro's name instead. `--discover-only` is what surfaced it. OpenCV's core module — 139 headers, 86,273 lines, `CV_EXPORTS` on every public class — reported `source: text scan` in 64 seconds, and the planner log said `constexpr evaluation hit maximum step limit`. The same discovery probe fails at `-fconstexpr-steps=100000000` and compiles clean at `2000000000`. The budget now escalates when the compiler says that is what went wrong, rather than being raised unconditionally, because raising it outright would make a genuinely runaway `constexpr` loop take twenty times as long to fail; `MB_CONSTEXPR_BUDGET` overrides the first tier so the path is testable without a codebase large enough to exhaust a real one. Two things the tests caught first. **GCC never escalated at all**: the guess at its wording, "maximum number of operations", matched nothing, while the real diagnostic is `'constexpr' evaluation operation count exceeds limit of N`, so GCC degraded in silence while clang worked — a bug in the shape that hides longest. And one assertion passed for the wrong reason, grepping stderr for "export macro" when the CLI's *own* text-scan fallback notice says that too, so it was green on a GCC run where nothing had escalated; it now matches a phrase only the escalation message carries. The escalation is reported on the terminal and not only in the log, because on a codebase large enough to need it the retry takes minutes and an unexplained wait of that length is indistinguishable from a hang. **It does not make a large codebase fast**: it converts a silently wrong answer into a correct, slow, self-explaining one, and the remaining cost is the single discovery translation unit rather than anything this fixes. At an absurd limit, incidentally, GCC 16.2 hits an internal compiler error in `coerce_template_parms` instead of reporting the limit, so the test uses measured per-compiler values rather than one small number.
- **Structural assertions on generated source are not tests, and the C# backend proved it.** Forty-seven checks passed against C# that no compiler accepts: the generated declaration read `private static extern intGet_id(IntPtr self)`, missing a space, which every check was happy with and `mcs` rejected immediately with fourteen errors. Compiling the output also caught the shim declaring `remove_cvref_t<Device>` — `display_string_of` on an alias prints the alias — and an unqualified `Device` in a translation unit with no using directives, since it prints an unqualified name; the fully qualified name is now passed in by the CLI, which had it all along. `mono-mcs` and `mono-runtime` are in the dev container and the test compiles the generated `.cs` and runs it, asserting on what comes out, including that a C++ throw arrives as a C# exception carrying `what()`. Where no C# toolchain exists the test says so explicitly instead of reporting a pass.
- **The benchmark page says what the measurement cannot resolve.** Every number in it is timed as `benchmark(name, lambda: ..., n)`, so each carries a Python loop iteration and a full Python function call on top of the operation. That constant is the same for all four frameworks, which means it does not cancel in a ratio: it pulls every ratio toward 1.00. Measured in the dev container at 28.3 ns for an empty lambda, which is 38% of a 74 ns null call. The floor is now measured on every run and published under the table, with the consequence stated: a ratio above 1.00x is a lower bound, one below understates the gap the other way, and a row within a few percent of 1.00 is not a tie that was measured. It lives under `_meta` because `check_ratios.py` gates every key under `mirror_bridge` and `test_published_rows.py` demands a published row for every key the runner writes, so a floor in either shape would be a meaningless gate entry and a meaningless row. Two rows also measured the wrong thing: "Attribute write" timed a list-subscript load, a store and an int add alongside the setter, and "Vector return (list out)" said `list` for a return that is an `array.array` — the claim the `.pyi` stopped making earlier in this release.
- **A declined method says which one and why.** A declined class and a declined free function were each refused by name on stderr; a declined *method* was refused in silence. Not on stderr, not in `--json`, not in the stub, and `dir()` simply does not list it, so a caller could not tell "I wrote the C++ wrong" from "that method does not exist". `docs/guides/accelerating-python.md` promises in writing that generate "reports every name you wrote that is not in the finished module, with the reason", and the gate computes three distinct reasons and printed none of them. They now reach the unbound report and the `--json` `declined` list as `kind: method`, in the same message shape the class-level ones use, so the CLI harvests them with the parser it already had rather than a second one. Behind `MIRROR_BRIDGE_REPORT_DECLINED`, which the CLI sets for its own verification import, because this runs at import and a large library declines hundreds: the tool sees them and a user's program stays quiet.
- **The agent-facing interface can reach the features built for agents.** The MCP server's `generate_bindings` took five parameters while the CLI accepts nineteen flags, so `--batch` — the largest shipped speedup for the acceleration use case, 6.8x from a list and 12.9x from an `array.array` — was unreachable from the one interface written for an agent, and so were `--link-args`, `--release-gil` and `-k`. `--stubs`, `.pyi` and `--batch` appeared nowhere in `AGENTS.md`, `quickstart.md` or `workflow.md`; they do now. Two more things it got wrong: the CLI's human-readable diagnosis goes to stderr and the wrapper discarded it, so a failed build reached the agent as one grepped line; and only one top-level field was translated from container paths back to host paths, so a path inside `errors[]` pointed at a filesystem the agent cannot see. The whole result is translated now, the `.pyi` comes back as `stub` and `stub_text`, and stderr is attached on failure. `tests/mcp_surface/` covers the argv and the translation, which had no tests at all, and cross-checks every flag the server emits against the CLI's own parser — a flag renamed on one side only is this project's recurring defect in its most literal form.
- **The CLI runs on macOS.** Every script here uses associative arrays or name references, both bash 4, and all five carried `#!/bin/bash`. macOS ships bash 3.2 from 2007 and will not ship a newer one, so the entire output of every subcommand, `doctor` included, was `declare: -A: invalid option` and exit 2. `docs/README.md` lists macOS as supported and every page says `./tools/mirror_bridge`; all fifteen CI `runs-on` entries are `ubuntu-latest`, so nothing was going to catch it. The shebang is `env bash` now, so a newer bash on PATH is used, and a guard above the first bash-4 construct says what is wrong and what to do about it. `tests/shell_portability/` pins the rule rather than the instance: any script using bash-4 syntax checks `BASH_VERSINFO` before reaching it. It found two more CLIs while being written.
- **A failed build keeps the file the compiler is complaining about.** The generated binding was deleted on the failure branch too, so the reader got one grepped line referring to line numbers in a file that no longer existed, plus "re-run with --verbose", whose output goes to stderr and which the MCP server discards. The `.cpp` now survives a failure, the terminal says where it is, and `--json` carries `generated_binding` so an agent gets a path rather than a bare line number. Two suggestions were added for errors that had none, including `no matching function for call to 'from_python'`, which is the most common real failure in the corpus and had no entry in the catalogue.
- **Three documented things that were not true.** The README said enums do not work, hours after they started working, and pointed at a closed issue; it said smart pointers work, which #54 says they do not in either direction; and it counted sixteen corpus libraries where the matrix publishes thirty-two. `docs/reference/cli.md` documented `init --name`, which the CLI rejects. `docs/guides/packaging.md` promised a `setup.py with auto-build` in `examples/packaging/`, which has four files and no build step, so following it produces a package that can only raise the ImportError its own `__init__.py` is written to raise.
- **Ten of the eleven numbered examples run again, and CI runs all of them.** Six were failing and had been for a long time, which nobody could see because the test harness globs `tests/` and the examples are not under it. That is the same blind spot that let `examples/open3d-comprehensive` ship with `o3d.PointCloud()` raising TypeError. Three asserted a `list` where a numeric vector has given an `array.array` for as long as the mapping has been documented, one called an overload under a mangled name the binder stopped emitting, one imported from the wrong directory, and one wanted enums, which now work. `tests/examples/test_examples.sh` builds and runs every one of them in 76 seconds, and takes its expectation from each example's own README: an example whose README carries a "not implemented" banner is expected to fail, and one that starts passing fails the test until the banner goes. `examples/10-smart-pointers` is the remaining failure and now says so, because `std::shared_ptr` is converted by value and the shared ownership does not cross the boundary either way (issue #54).
- **The generated `.pyi` says `array[...]` where the runtime hands back an `array.array`.** A `std::vector<double>` crosses as `array('d')` and the stub said `list[float]`, which is worse than saying nothing: a type checker then approves `result + [1.0]` and `json.dumps(result)`, and an agent reading the stub to write the call has no way to find out. `type_hint` was one function serving three positions with three different right answers, so it now takes the position. Returns say what comes back. Parameters keep `list[T]`, deliberately: the ingest side takes a list, a tuple, an `array.array` or any buffer, and the obvious spelling for that, `Sequence[float]`, admits `bytes`, which `from_python` rejects outright, so it would approve a call that fails. A member whose read and write differ now renders as a property with a setter, and only where they differ, so an ordinary member stays an ordinary annotation. The decision itself moved next to the stub generator and `to_python` now reads it from there, because two copies of it is how the stub came to disagree with the runtime in the first place.
- **Three smaller things the stub was wrong about.** `char` is arithmetic and signed, so it crosses as an `int` in both directions and the stub said `str`. `bytes` has exactly one producer, `std::vector<unsigned char>`, while the stub also claimed it for `std::vector<char>`, `std::vector<std::byte>` and `std::array<unsigned char, N>`, all of which come back as lists of `int`. And a numeric vector the `array` module has no typecode for, such as `std::vector<long double>` or `std::vector<signed char>`, is a list: the stub mirrors the typecode table rather than approximating it with "numeric".
- **The two stub generators give one answer.** `scripts/generate_stubs.py`, which `mirror_bridge_auto` runs, rebuilt a stub by importing the finished `.so` and reading docstrings off it. Every module mirror_bridge builds already carries one written from the reflection the binding was written from, which knows the real C++ parameter names, the exact member types and the `array.array` return. The script asks for that first now and keeps the reconstruction for a module that has none.
- **`llms.txt` matches the generator that writes it.** The curated index is a hand-written list of link lines in `tools/gen_llms_txt.sh`, and the accelerating-python guide had been added to the committed file and not to the list, so the next run would have silently deleted it. `llms-full.txt` was 1,300 lines behind besides. `tests/llms_sync/` runs the generator into a temporary directory and diffs, the same contract `check_single_header_sync.sh` holds the single headers to.
- **A class whose `value_type` is unrelated to what iterating it yields binds again.** Converting a container casts the dereferenced item to the container's `value_type`, which is what keeps a `std::vector<bool>` proxy from reaching Python as a dict. Nothing checked that the cast existed. `Json::Value` declares `value_type` as `std::string` and hands back a `Json::Value`, and a hard error inside a conversion template fails the whole module rather than that one conversion, so jsoncpp went from binding to not building at all. The cast is now made only where it is valid, asked as `is_constructible_v` and not `is_convertible_v`, because a proxy's conversion operator is usually explicit and the second trait reports false for exactly the case the branch exists to catch. `tests/data_model` gains both shapes side by side.
- **The compatibility matrix stops blaming a warning for a compile error.** The CLI prints `'Factory' is the binding name of 2 classes`, picks the one in the shallowest namespace and carries on, so that line is advice. The failure classifier matched it anyway and published jsoncpp as a name collision while the real failure was a conversion two thousand lines away, which is worse than saying `compile-error`: a category is a claim that we know what the problem is, and this one sent the reader after the wrong bug. It now matches the compiler's own `redefinition of` instead. The classifier had no tests, and the file that tests it has moved from `compatibility/` to `tests/compatibility_matrix/` because the bash harness is the only thing CI runs and it only looks under `tests/`.
- **A returned object carries the type of the module that returned it, whatever was imported last.** Constructing a bound class goes through that module's `tp_new`, which can only produce that module's type object. Returning one by value went through `to_python`, which asked the shared registry in `sys.modules` first, and that registry holds whichever module registered last. So `isinstance(m.Maker().make(), m.Part)` was False, and which module's type the object actually carried flipped with the order of the imports above it, which is the thing Python code type-checks with. One question, which `PyTypeObject` represents a class in this module, was answered in three places and two ways: the inbound conversion asked this module's own registry first and wrote a cross-module hit back into it, with a comment explaining why, and the two outbound conversions did the opposite with no comment. All three now call one function. Returning a bound object falls from 34.9 ns to 25.4 ns as a consequence, with returning a `double` and constructing flat as controls, because the common case is a load and a compare rather than a dict probe. Two modules binding one class still build two type objects, which is the other half of the problem and is not fixed here.
- **`bind_class_auto` works again for a class whose constructor takes arguments.** Every construction of such a class raised `TypeError: ... is already initialised`, the zero-argument one included, so the flagship `examples/open3d-comprehensive` could not build a `PointCloud` at all. `bind_class` puts the object together in `tp_init` when the class has a parameterized constructor and in `tp_new` when it does not, and `bind_class_auto` replaced only `tp_new`, with a slot that constructed unconditionally. The suite stayed green because its one auto class declares nothing but a defaulted constructor, and nothing in CI runs `examples/`. Underneath it was one construction path written twice: `py_new_auto` did its own `new T()`, which is also why these classes never got the inline payload, never set `parent`, silently discarded constructor arguments and had none of `py_new`'s diagnostics for an abstract or non-default-constructible class. It now delegates to `py_new` or to a new `py_init_auto`, and adds only the vtable swap. The slots travel into `bind_class` and are chosen before `PyType_Ready` rather than written over the type afterwards: `PyType_Ready` copies `tp_init` into the `__init__` descriptor it builds, so a later overwrite is not what `super().__init__()` calls. Measured, because that failure is silent rather than loud -- with the slot patched afterwards the object constructs correctly and C++ then calls the base while Python calls the override. One behaviour change falls out: an auto class with no parameterized constructor now refuses `Cls("x")` with the same message `bind_class` gives, where it used to drop the argument.
- **The monthly benchmarks refresh publishes again.** The job regenerates two tables and opens a PR with them, and two of its checks deliberately run after that PR so that a red build cannot cost a month of numbers. The trading splice was not written that way. `format_trading_results.py` refuses to render when numpy was absent, rightly, since the page would otherwise claim a vectorised comparison it never made, and the benchmark image installs jupyter, pybind11 and nanobind but never installed numpy or scipy. So the refusal fired on every run and killed the job before the PR step, taking with it a runtime table that had already regenerated cleanly. That is why the published page still listed seven of the twelve measured operations weeks after the formatter was fixed to emit twelve, and why `benchmarks/ratio_floors.json` never landed, leaving the ratio gate with nothing to gate against. numpy and scipy are now in the benchmark image, the trading splice records its refusal and leaves the committed table where it is, and the failing is done by a step that runs after the PR exists. `tests/benchmark_table/test_refresh_contract.py` feeds the step's own shell to `sh -e` and watches what it does, which is what nothing was doing: the rule was written in a comment in the workflow and checked by no one.
- **A member whose type has no default constructor no longer fails the whole module.** The attribute setter converts into a local and moves it into place, and that local needs a default constructor, so one such member was a compile error for every class in the module rather than for the one attribute. It is now readable and not assignable, which is the answer a `const` member already got three lines above. `nlohmann::detail::dtoa_impl::diyfp` declares only `diyfp(uint64_t, int)`, and a class holding one was most of why nlohmann-json counted as a compile failure.
- **The generated `.pyi` describes the members the module actually binds.** It walked every data member and asked only whether the type was `const`, while `bind_class` walks the visible members and weighs the annotation, constness and assignability. So a `[[=exclude{}]]` field appeared in the stub while raising `AttributeError` at runtime, and a `[[=readonly{}]]` field was described as writable. On the project's own example that meant the stub promised `password_hash` and `internal_flag` -- a type checker approving exactly the access the annotation exists to prevent. Both now ask one shared predicate.
- **Namespaces a macro opens no longer poison the generated binding.** The `using namespace` lines are read from header text, which cannot expand a macro, so nlohmann-json's `NLOHMANN_JSON_NAMESPACE_BEGIN` produced `using namespace detail::detail::detail;` and seventeen errors before the first line of binding code. They exist only so unqualified names from the text scan resolve, and are now emitted only for it; reflection reports names in full.

### Added
- **The `.pyi` is written by default.** `--stubs` was off, and `--stubs` and `.pyi` appear nowhere in `AGENTS.md`, `quickstart.md` or `workflow.md`, so the artifact that tells a reader, an IDE, a type checker and an agent what the module exposes was only written by someone who already knew to ask for it. It costs one import of a module that was just built, against a generate that takes seconds to minutes. `--no-stubs` opts out, and the default lives in the one place that decided it before.
- **An enum reaches Python as an enum.** The values always crossed correctly, as plain `int`. The types did not, so a module with a `Color` parameter exposed 0, 1 and 2 with nothing in it saying which was which, and `book.add(99, ...)` was accepted. Each enum the CLI discovers is now bound as an `enum.IntEnum` carrying the C++ enumerator names and values, and the stub declares it and annotates members, returns and parameters with it instead of `int`. Nothing about the conversions changed, because an `IntEnum` member is an `int`: a function that took a bare int still takes one, and one that returns an enum still returns a bare int, which compares equal to the member. An enumerator whose name is a Python keyword gets a trailing underscore, because `Permission.None` is a syntax error rather than a failed attribute lookup, so there would be no spelling for a caller to find. Scoped, unscoped, nested and negative or non-contiguous values all work. Lua and JavaScript have no enum object to map onto, their values keep crossing as numbers, and the CLI's unbound report now says which backend does which. Closes #20, including its open question: enumerator values come out through an ordinary splice, where `display_string_of(constant_of(e))` had returned `(unsupported-reflection)`.
- **`--batch`: a method you call in a Python loop gets a sibling that takes the whole sequence.** For each method taking and returning exactly one arithmetic value, `<name>_batch` is generated from reflection, so the boundary is crossed once instead of once per element. Measured over 100,000 elements: 6.8x from a list and 12.9x from an `array.array`, which is what another batch call returns. It carries state across the loop, which a list comprehension cannot be rewritten to do. Off by default because each sibling costs compile time -- +12% on a class with ten eligible methods, +55% with forty -- and because it is 1.0x when the method itself is the expensive part, the boundary having never been the cost. Generated rather than asked for: the header previously told the C++ author to write `process_batch` by hand, which is the team that owns the header doing work for the team that consumes it. Never generated over a `<name>_batch` the author wrote, and never for an overloaded name, a `bool`, a `void` return or anything non-arithmetic.

### Fixed
- **The Python header compiles on GCC again, and annotations are honoured there.** `#include "python/mirror_bridge_python.hpp"` had stopped compiling under `g++ -std=c++26 -freflection`: a helper added to the clang arm of a `#if defined(__clang__)` fork was called from the GCC arm, where it did not exist. Behind that, the GCC arm was a stub that ignored every annotation, on the belief that P3394 was a clang-p2996 extension. It is not: both standard libraries implement it, and both spell `std::meta::annotations_of` the same way. Measured against the last header version that compiled on GCC, a field marked `[[=exclude{}]]` was exported to Python under its own name and was writable, and a `[[=readonly{}]]` field accepted writes. The fork is gone: there is now no compiler-conditional code in the annotations header at all. `tests/annotations/` asserts the runtime behaviour, which nothing did before -- the existing test compiled a binding with annotations and checked nothing about what they did, so it could not tell an honoured annotation from an ignored one.
- **A returned numeric vector is copied once rather than twice.** `std::vector<double>` and friends crossed into an `array.array` by way of an intermediate `bytes` object that was copied from and then immediately discarded. `array.frombytes` accepts any buffer, so a memoryview over the container's own storage stands in for that copy. Worth 1.47x to 1.64x from 32 KB up and 1.02x at 800 bytes; below 1 KB the extra interpreter call costs more than the copy saves, so the old path is kept there.
- **The benchmarks page publishes every operation it measures.** The runtime suite measures twelve operations per framework and the page showed seven, because the formatter's row list and the runner's result keys disagreed on three names and omitted two more. Attribute read and write, the most frequent operation on a bound object, had never appeared in the published comparison, nor had the list-in direction. A drop is now named on stderr and fails the refresh under `--strict`, and `tests/benchmark_table/` pins the two lists together.
- **The ratio regression gate fails when it has nothing to compare against.** `check_ratios.py` measured its floors and returned 0 when `benchmarks/ratio_floors.json` was absent, which reads the same as a passing gate, and did the same for floors that were `null`, empty, or keyed by operations the run no longer measures. All four now fail under `--require-floors`, which CI passes.
- **Class discovery reads the headers through reflection, not as text.** `generate` tokenized the header text and took the identifier after `class`/`struct` as the class name. In a shipped C++ library that identifier is almost never the class: `class JSON_API Value`, `class V8_EXPORT Isolate`, `class CV_EXPORTS Mat`, `class LLVM_ABI Module`. Pointed at jsoncpp's headers the CLI reported 23 classes, all of them named `JSON_API`, and emitted twenty copies of `bind_class_when_bindable<JSON_API>`; it now reports `Json::Value`, `Json::Reader`, `Json::CharReader::Factory` and the rest. It is not only macros — `struct alignas(64) Wide` bound a keyword, and `struct [[nodiscard]] Tagged` was dropped without a word. The reflection pass that gets this right already ran in the same command for the template planner; nothing read its answer. Nested classes and declaration sites are now part of what it reports, and the walk skips type aliases before recursing (`using iterator = ValueIterator;` is a class type, and following it ran the discovery unit into the constexpr step limit on jsoncpp). When the headers cannot be compiled on their own the text scan still runs, and `generate` says which list it is using.
- **Discovery is confined to the directory `generate` was pointed at.** Reading the headers after the preprocessor has run means reading the whole translation unit, third-party headers included, and a header was matched to the project only by the end of its path. A project with a `config.h` that includes a vendored `vendorlib/config.h` got both, so `lib::VendorInternal` and everything beside it entered the module — compiling and shipping, with nothing said. Pointing the CLI at a directory containing `value.h` and a vendored jsoncpp put all ten `Json::` classes in the module and the build then failed inside jsoncpp's own container shape. The suffix match is now anchored to the resolved source directory, which also stops `/x/src` from matching `/x/src_vendor/`. On jsoncpp the same collision was also costing a whole planning pass, because `in_source` is what `ours()` and `inventory()` use as well: libc++ spells one of its own headers `__memory/allocator.h`, which ends the same way as jsoncpp's `allocator.h`, so `std::allocator` read as ours, the foreign entities that let into the planner's universe made the first planning attempt fail, and it retried with a reduced header set. `generate` on `jsoncpp/include/json` goes from 73.7s to 17.9s on an idle 16-core box, and the module gets back the six headers the retry had been dropping. That part is the cost of one collision disappearing, not a general speedup — where no header name collides, the walk still costs the ~9% it says it does.
- **A reflection pass that reports no class falls back instead of emptying the module.** The walk does not enter an anonymous namespace, or one whose name starts with an underscore, so headers whose classes all live there compiled clean and produced an empty list, and `generate` then stopped with "No classes found" on a header that built a working module before. The text scan's answer now stands when reflection names nothing at all, and the message distinguishes a walk that found nothing from a reflection unit that would not compile — the two have different causes and only one has a log to read.
- **A header set with no classes in it no longer stops the CLI.** Templates and free functions alone are an ordinary surface, and an empty class list expanded to one empty word where the CLI wanted an array subscript: `generate` on such a directory died with `bad array subscript` before it reached the planner, where it used to build the module.
- **`--output` below a directory that does not exist yet keeps reflection on.** `realpath` refuses a path whose parent is missing, so `--output build/py` on a clean tree stayed relative; the planner's working directory under it was then unreachable from the compiler, which runs with the source directory as its cwd. The discovery unit failed for a reason that had nothing to do with the headers, discovery fell back to the text scan, and the CLI reported that the headers did not compile.
- **Two classes with one binding name no longer claim the build will fail.** It does not: the generated file names each class in full, so the collision is in the target language, where the last class bound is the only one reachable under that name. The warning says that instead, and offers `MIRROR_BRIDGE_SKIP`, which now does resolve it.

### Added
- **Bound classes answer the Python data model: `for x in obj`, `len(obj)`, `x in obj`, `pickle.dumps(obj)`.** All four raised `TypeError` before, whatever the C++ type offered, and they are what a team hits in week one through `multiprocessing`, `copy.deepcopy` and a plain `for` loop. Nothing is declared per class. A type whose `begin()`/`end()` form a range over convertible elements gets `tp_iter`/`tp_iternext` generated with `++it`, `*it` and the sentinel comparison as splices; `end()` may return a sentinel of its own type as a C++20 range does, and the element is taken from `std::iterator_traits<It>::value_type` where the iterator has traits, so `std::vector<bool>` yields booleans rather than the proxy reference `*it` returns. Membership falls out of that, because with no `sq_contains` CPython searches by iterating; a range that is also `size()`-able gets `mp_length` and `sq_length`, and a `size()` too large for a `Py_ssize_t` — an unsigned count that underflowed — raises `OverflowError` naming the class and the value instead of reaching CPython as a negative length. A default-constructible class gets `__reduce__`/`__setstate__` over the reflected member list — the same walk `__repr__` does, so a member added in C++ joins the pickle by itself instead of being forgotten by a hand-written `py::pickle()` that lists every field twice — and only when the state can carry every member and put it back: a `const` or `[[=readonly{}]]` member, a `private` or `[[=exclude{}]]` one the visible member list does not report, or a member a base class declares each keep `pickle.dumps` raising `TypeError`, because each would otherwise load into an object that looked right in `repr()` while holding a default value for that field. Iterating a million ints costs 6.99 ns per element against 50.08 for pybind11's `make_iterator` and 14.22 for nanobind's, and 6.74 for CPython's own `range`, which is the floor: fastest of nine runs, collector off, one framework per process, same compiler and flags.
- **The generated iterator holds a reference to the container, so it cannot dangle.** pybind11 makes the author ask for this with `py::keep_alive<0, 1>()` and reads freed memory if they forget; here it is what the slot does. `for x in make_bag()` drops the last Python reference to the container the moment the loop starts, and with the reference removed that exact test segfaults under `PYTHONMALLOC=debug`, while the shipped slot walks all 1000 elements correctly and frees the C++ object once the iterator goes. Mutation is a separate problem that no ownership scheme solves — a reallocation invalidates C++ iterators no matter who holds the memory — so the generated iterator checks two things each step: the element count, CPython's own answer for `dict` and `set`, raising `RuntimeError: Bag changed size during iteration`; and whether `begin()` has moved, raising `RuntimeError: Bag reallocated its storage during iteration`, which is what catches a `reserve()` or a `shrink_to_fit()` that relocates the buffer without changing the count. Neither check sees a mutation that preserves both the count and the buffer — an `erase` paired with a `push_back` — so iterating a container while mutating it stays undefined exactly as it is in C++; the guards turn the common accidents into an exception rather than a wrong number. `docs/reference/type-conversion.md` has the table of what is and is not caught.
- **`__iter__` and `__len__` are written into the generated `.pyi`** for the classes that have them, so a type checker agrees with what the module does: `for value in bag` and `len(bag)` now pass `mypy --strict` where they were `"Bag" has no attribute "__iter__" (not iterable)`. `Iterator` is imported only when a class in the module declares `__iter__`, so a module with no ranges keeps the stub it already had and a committed `api --check` baseline moves only when the surface does.
- **Methods, static methods and free functions are called through the vectorcall protocol.** CPython hands a fastcall entry point a flat array of borrowed references; the previous `METH_VARARGS` entry point made it allocate an argument tuple and a keyword dict per call and tear both down. At zero arguments the two conventions already measured the same, which is what identified the tuple rather than the design as the cost: the gap grew about 2ns per argument. Keyword calls gained most, 87ns to 33ns.
- **Scalar conversion no longer leaves the header in the common case.** An exact Python float is one macro load, and an int small enough for CPython's compact representation is a load and a sign flip, read directly below 3.12 and through the public `PyUnstable_Long_*` accessors from 3.12 on. The public readers are calls into libpython that cannot be inlined, and on an 80,000-element list that call was the whole difference between the integer and floating-point ingest paths. Anything the fast path declines — a wider int, the stable ABI, PyPy — falls through to the public API.
- **Lists and tuples of exact scalars convert through a bulk tier** that needs neither the per-element size re-read nor the `from_python` dispatch the general tier needs. A non-exact element is not an error: the tier stops and the general one resumes at that index.
- **Trading workload benchmarks** (`benchmarks/runtime/shared/trading_bench.hpp`): a price-level order book, Black-Scholes over a contract vector, and an EWMA crossover driven at every chunk size from 1 to 262,144. Each framework is timed in its own interpreter, fastest of nine runs with the collector off, because sharing a heap made the third-timed framework read up to 30% slow.
- **Generated modules are built with `-fvisibility=hidden`.** A module was exporting every template instantiation the reflection pass produced, 170 of them on the benchmark class. Through the CLI the module goes from 109,336 to 92,512 bytes, a 15.4% cut, almost all of it symbol tables and relocations. Lua's `luaopen_` entry point is now marked with a new `MIRROR_BRIDGE_EXPORT`; `PyMODINIT_FUNC` and `NAPI_MODULE` already carried the attribute.
- **`mirror_bridge api`: gate a module's Python surface on a committed stub.** Generating a module is the easy half of running this in production; the hard half is the Python team finding out when the C++ team changes something. The generated `.pyi` is the one artifact that cannot drift from the binding — it is filled in during `bind_class` from the same reflection data — and it is byte-identical between runs and between clang-p2996 and GCC 16, so it can be committed and compared like a lockfile. `api --update` writes the baseline, `api --check` fails CI when a name disappears or changes signature, and additions pass because nobody's import breaks when a method appears. The report classifies the diff rather than printing it, so a C++ pull request shows which names the Python team is about to lose. New guide: `docs/guides/independent-teams.md`.
- **GIL release policy**: `bind_class<T>(...).release_gil()` (or `mirror_bridge generate --release-gil`) drops the GIL while C++ method bodies run, so long native calls stop blocking other Python threads — 4 threads × 150ms native sleep now finish in ~150ms instead of ~600ms (regression-tested in `tests/gil_release/`). Safe by construction: `std::function` callbacks and virtual-override trampolines re-acquire the GIL themselves, so no per-method signature reasoning is needed. Zero overhead when not enabled.
- **Free-threaded CPython declaration**: compiling a module with `-DMB_FREE_THREADED` on Python 3.13+ declares `Py_MOD_GIL_NOT_USED`, preventing a mirror_bridge module from silently re-enabling the GIL process-wide on free-threaded builds (opt-in, mirroring nanobind's `FREE_THREADED` flag). New guide: `docs/guides/threading.md`.
- `bind_class` now returns a fluent `BoundClass<T>` handle (implicitly converts to `PyTypeObject*`, so existing code is unaffected) — the home for per-class binding options like `release_gil()`.
- **Reflection-exact `.pyi` stubs**: every module now exposes `__mirror_bridge_stubs__()`, populated automatically during `bind_class` from the same reflection data the binding is generated from — exact member types, constructor overloads (`@overload`), real C++ parameter names, `@staticmethod` markers, Eigen/container/map type hints. `mirror_bridge generate --stubs` writes `<module>.pyi` next to the built module. No runtime parsing: stubs cannot drift from the binding.
- **Header-to-wheel scaffolding**: `mirror_bridge init <name> --wheel` emits pyproject.toml (scikit-build-core), a CMake build consuming mirror_bridge via find_package/FetchContent, an explicit binding TU, and a wheel-building GitHub workflow. Validated end-to-end: `pip wheel . && pip install dist/*.whl && python -c "import <name>"` works from a fresh scaffold.
- **Stock GCC 16+ support**: mirror_bridge now compiles with upstream GCC's C++26 reflection (`g++ -std=c++26 -freflection`), not just Bloomberg's clang-p2996 fork. The CLI, `mirror_bridge_build`, doctor, and test runner auto-detect the available reflection compiler (override with `MB_CXX`).
- `mirror_bridge init <name>` scaffolds a ready-to-build project: example header, per-language smoke tests, README, and a GitHub Actions workflow that builds and tests the bindings in the reflection container
- **Bulk container ingest**: `from_python` for numeric containers accepts any contiguous buffer (`array.array`, NumPy arrays, `memoryview`) via a single memcpy — the ingest mirror of the existing `array.array` return path
- List/tuple fast paths in container and Eigen conversion (borrowed-reference access, `PyFloat_AS_DOUBLE` for exact floats): the 1M-point `list[[x,y,z]] -> vector<Eigen::Vector3d>` ingest went from 18.4ms to 12.2ms (28x -> 42x vs pybind11 on the fair benchmark)
- **By-reference argument passing**: lvalue-reference parameters of bound classes (`const T&`, `T&`) now alias the Python-held object instead of copying it — zero copies for `const T&`, and `T&` mutations are visible from Python (matching pybind11 semantics); regression-tested with an instrumented copy counter
- `find_package(mirror_bridge)` now delivers the same `mirror_bridge_python_module()` / `_lua_module()` / `_js_module()` helper API as add_subdirectory/FetchContent (helpers moved to an installed `MirrorBridgeModules.cmake`); helpers gained an `OUTPUT_DIRECTORY` argument and lazy dependency lookup
- CMake integration guide (`docs/guides/cmake.md`)

### Changed
- **A bound class's `tp_name` is now `<module>.<Class>` rather than the bare class name.** CPython reads a static type's `__module__` out of the text before the last dot, so every bound class claimed to live in `builtins` and pickle could not find the class it had just serialized. `__name__`, `__qualname__` and the generated `__repr__` are unchanged — the first two are defined as the text after the last dot — so what moves is `__module__`, and the type name CPython prints in its own error messages, which now reads `'orders.Book' object is not subscriptable` instead of `'Book' object ...`.
- **`bool(obj)` on a class that is both iterable and sized is now `len(obj) != 0`.** A length slot is not a neutral addition: with no `nb_bool` CPython derives truthiness from it. Gating `mp_length` on `size()` alone would therefore have redefined `if obj:` for every class that merely has a method spelled `size()` — a gauge reading, a kernel width — so `len()` is offered only where `begin()`/`end()` say that "how many elements" is the question `size()` was already answering. For those classes empty-is-falsy is the correct Python semantics rather than a change of meaning, and `nb_bool` is written out instead of left implicit so the decision lives in the source. A class with `size()` and no range keeps both its truthiness and its absence of `len()`. **This is a silent behavior change for existing code** and it reaches further than `if obj:` — `assert obj`, `obj or fallback`, `filter(None, objs)`, `any`/`all` and a truthiness comprehension filter all change with it. The case to look for is a container-shaped class used as a handle: a `Connection` that exposes a queue through `begin()`/`end()` and `size()`, where `if conn:` used to mean "I have a connection" and now means "my queue is non-empty", which reads the same and silently stops sending. Write `if conn is not None:` for an existence check. There is no per-class opt-out — truthiness follows from the length slot — and a range *without* `size()` has no length slot, so it stays truthy when empty; `docs/reference/type-conversion.md` spells out the asymmetry.
- Pack expansions over reflected parameter types use alias templates (`method_param_t`, `static_method_param_t`, `*_constructor_param_t`, `virtual_param_t`) instead of inline splices, so the parameter pack is visible to both GCC and clang.
- `PyTypeObject`/`BufferView` initializers designate `.ob_base` so GCC accepts them alongside the other designated fields.
- CLI Lua modules are emitted to `<output>/lua/<module>.so` — Python and Lua both produced `<module>.so`, so `generate --lang all` silently overwrote one with the other
- `ctest` now registers exactly the tests whose modules the CMake build produces (bash-harness-only tests are excluded and remain covered by CI's bash jobs); test files prefer freshly built modules over stale artifacts in `build/`
- `tests/run_all_tests.sh` no longer treats the template planner's scratch units as bindings. It builds every `.cpp` under `tests/`, which picked up the `discover.cpp`, `probe.cpp` and `request.cpp` the CLI tests leave in their work directories; those only compile with their generated inputs beside them, so every run after the first reported up to ten failed bindings on a tree that was otherwise green.
- Benchmark documentation consolidated: `docs/internals/benchmarks.md` (CI-regenerated monthly) is the single canonical results page; stale/contradictory results docs removed, and the runner no longer records zero-filled placeholders for frameworks that failed to build
- CMake compiler check and package config understand GCC 16+ (previously warned that only clang was supported)
- Removed the unused `ClassMetadata`/`Registry` pair from `core/` — the Python backend's registry (the only one ever used) is the single implementation

### Changed
- **Calling `__init__` on an object that already holds one is refused.** It used to construct a second object and abandon the first, which leaked it. Writing over the storage in place skips the old object's destructor, and with the inline payload a constructor that throws part way leaves members that unwinding has already destroyed for `tp_dealloc` to destroy again, which aborted the process with a double free. Freeing the old object first fixes both and introduces something worse: a member view holds a raw pointer into the owner's storage, so freeing it leaves the view reading freed memory, and there is no view count to consult. The first `__init__` after `__new__` is unaffected, since the pointer is null there; a second one now raises `TypeError` naming the class and saying to construct a new object. An object whose construction failed outright still reports that it holds no C++ value, and now says why rather than "Invalid C++ object".
- **Returning a bound class by value is 3.4x faster, and the C++ object now lives inside the Python object.** Returning a bound class cost 111ns against 20ns for returning a `double`, and the gap did not move with the size of the object (264 bytes measured the same as 24), so it was never the copy: every return re-found the type registry in `sys.modules` and then the type in it, two `PyDict_GetItemString` probes that each build a `str`, hash it and throw it away. Both are stable for the life of the process and are now cached, the registry behind a strong reference and the per-type key as an interned `str` that carries its hash. This is deliberately not the inverted-priority fix that was proposed for it: reading the per-module static before the shared dict would break cross-module object identity, because the dict is the canonical type for a class bound in more than one module. On top of that, the payload is placement-constructed inside the Python object instead of behind a second allocation, which `tp_basicsize` now accounts for, so an ordinary bound object costs one allocation rather than two. Abstract classes, over-aligned classes and virtual-override trampolines keep the heap path, and the wrapper tells the two apart in `tp_dealloc` by where the object sits rather than by carrying a flag. Measured on the same machine, floor of 11 over 200k iterations with the collector off and one process per build: returning a 24-byte object 111.4ns to 32.7ns, a 264-byte object 110.8ns to 37.8ns, constructing 38.8ns to 33.0ns, with a null method call and a `double` return unchanged as controls. Covered by `tests/wrapper_alloc/`, which compares the payload's address against the Python object that owns it, because a count of destructions is the same on both paths, and runs clean under `PYTHONMALLOC=debug`. Two things had to be corrected before it was safe. An auto-trampoline class released its object with `delete` whatever the payload was, so the first `bind_class_auto` class returned by value aborted the process with `free(): invalid pointer`, and the same function never released the reference a member view holds to its owner. It now goes through the one function that knows where the object sits, which is what `tp_dealloc` already used. The other is what two modules do when they disagree. `tp_basicsize` now depends on `sizeof(T)`, so two modules built against different revisions of the same header want different wrapper sizes under one `typeid` name, and the module that returns the class by value was handed the other's type object and placement-constructed its larger payload into the smaller allocation. Measured on GCC 16 at 176 bytes into a 48-byte object, which segfaults. Every mechanism that could have caught it was itself a static of a template, which the dynamic linker merges across modules unless they were compiled with hidden visibility, so the first module to load decided the answer for both. The cross-module key, the interned copy of it and the per-module type cache are now named by the wrapper size as well, which makes them different symbols with nothing to merge, and a lookup across a disagreement misses and degrades to a dict snapshot. Where both modules bind the class, the type object itself is the shared static, and `bind_class` now refuses the second import and names both sizes rather than allocating through a type it did not size. The CLI already compiled with `-fvisibility=hidden`. The CMake helper and the test harness did not, and now do, which is also where the 170 exported template instantiations per module were going. Covered by `tests/abi_skew/`, which is two modules whose headers disagree about one class, run both ways, and by `tests/auto_trampoline/`. Both crash rather than fail without the fixes.

### Fixed
- **A C++ name that is a Python keyword produced a `.pyi` that nothing could parse.** Parameter and member names were emitted verbatim, so one `double scale(double lambda, double vega)` was enough to make the stub invalid Python, and a type checker rejects the whole file over one bad line. It also made the module impossible to put under `mirror_bridge api`: `--update` wrote the unparseable baseline and reported success, and `--check` then failed on every run with no C++ change that could fix it. A parameter is now renamed and marked positional-only with PEP 570's `/`, which is the truthful description -- the runtime still answers to the real C++ name through `f(**{"lambda": x})`, and no Python source can write `lambda=x` either way. A member whose own name is a keyword has no declaration form at all, so it is omitted with a comment saying why and `generate` names it on the console. A parameter called `self` collided with the receiver and is renamed the same way. Stubs for keyword-free modules are byte-for-byte unchanged, on both clang-p2996 and GCC 16. Covered by `tests/pyi_keywords/`.
- **A static method's and a free function's stub said their parameters could be passed by name.** Neither accepts keyword arguments at runtime -- both raise `TypeError: takes no keyword arguments` -- so a type checker was blessing calls that fail. Both are now rendered positional-only, which is what `/` is for. This changes the committed `.pyi` for any module with a static method or free function that takes parameters, three of the eight example modules, so `mirror_bridge api --update` is needed once; the surface itself has not changed, only the description of it has stopped being wrong. An unnamed C++ parameter is marked the same way, since there is no keyword for it either.
- **A substituted parameter name could claim a real one.** `double f(double lambda, double lambda_)` rendered as `lambda_, lambda__`, which advertised `lambda__` -- a keyword the module refuses -- and hid `lambda_`, which it accepts. The names the runtime answers to are now reserved before any substitute is invented.
- **The CLI put the working directory ahead of its own headers.** The compile line read `-I. -I$src_dir -I$PROJECT_ROOT`, so running `mirror_bridge generate` from a directory holding a `mirror_bridge.hpp` -- a vendored copy, or the repository itself while generating for another project -- built the module against that header rather than the installation's, silently and with no diagnostic. `PROJECT_ROOT` now leads, in the module compile and in the planner.
- `generate --stubs` now parses the stub it just wrote and says so loudly if it does not compile, and `api --update` refuses to store a baseline that does not parse rather than wedging the gate.
- **`core::type_key` gave two distinct types the same name.** The key is the cross-module identity of a bound class — the registry key Lua's metatable lives under, and the value the JavaScript tag compares — so two types sharing one is exactly the confusion the boundary checks exist to prevent. Two ways in. `spell()` tested `is_pointer_type` before `is_const`, and `remove_pointer` drops the qualifiers on the pointer itself, so `Box<int* const>` spelled as `Box<int*>`; the order is fixed. And a spelling that falls back to `display_string_of` is implementation-defined, which the spelling header's own comment says it avoids for this reason: clang-p2996 renders every enum-valued template argument as `(unsupported-reflection)` and every unnamed type as `(anonymous type)`, so `EnumParam<Colour::Red>` and `EnumParam<Colour::Green>` came out identical. That case is now a `static_assert` in `bind_class` instead of a silently shared identity. `tests/type_key/` pins both, plus the spellings that must not move.
- **A write through a nested data member was silently discarded.** `o.p.x = 7.0` left `o.p.x` at `0.0` with no error, because the getter handed back a wrapper around a fresh heap copy and the write landed on the copy, which the expression then dropped. A non-static data member is interior to the wrapped object by construction, so the getter now returns a view onto the owner's storage holding a strong reference to the owner. That is settled at compile time from the reflected member list: unlike a method return it needs no return value policy from the author and no runtime instance lookup, which is the part pybind11 and nanobind cannot copy, since they receive a member pointer and nothing else. Reading a member no longer copies at all, measured 1000 copy constructions to 0 with an instrumented copy constructor. Method returns are deliberately unchanged -- interiority cannot be established for them, and the inference that was proposed fails in both directions -- and container elements are deliberately excluded, because a view into a `std::vector` dangles the moment it reallocates. Covered by `tests/member_views/`.
- **Cross-module type sharing is now keyed on the wrapper layout as well as the type.** The forward registry hands out one `PyTypeObject` per C++ class process-wide and `tp_basicsize` comes from whichever module registered it first, so two modules built against different revisions of the header disagreed about how big a wrapper is and the newer one would write its trailing fields past the end of an allocation the older one sized. That is a heap overflow rather than a wrong answer, and it was reachable as soon as the wrapper grew a field. Every cross-module key now carries a layout tag, so a mismatched pair simply does not recognise each other's objects and the failure is a `TypeError` at the boundary. Matching builds share types exactly as before. Because the resulting conversion failure names a class whose name looks correct, a module that finds another layout already loaded now says so once at import, as a `RuntimeWarning` naming both layouts, rather than leaving the `TypeError` to be puzzled over.
- **A C++ exception thrown from a bound free function or from a constructor aborted the process.** It unwound past the interpreter and `std::terminate` ended the session with exit 134: no traceback, nothing catchable. Instance methods and static methods were already wrapped; these two paths were not, and a constructor that validates its arguments and throws is ordinary C++.
- **Constructing with keyword arguments silently produced a default object.** `py_init` read `PyTuple_Size(args)` and never looked at `kwds`, so `Cls(a=1, b=2)` had `nargs == 0`, fell into the default-construct branch and reported success — the caller got an object built from none of their values and no error. Keyword arguments now resolve against the constructor's reflected parameter names, so mixed and out-of-order calls work and an unknown name is refused rather than ignored.
- **Integer arguments are range-checked.** The old path was an unchecked cast, so `2**31` into a C++ `int` arrived as `-2147483648`, and `2**200` arrived as `-1` with an `OverflowError` left set on the thread to be reported later by whatever unrelated call next entered CPython. Out of range is now a `TypeError` at the boundary with nothing left pending.
- **A failed call says why.** Four different mistakes previously produced the same line, naming neither the bad keyword, the arity wanted, nor the parameters that exist. Where exactly one overload competed for the call, the message now reads `scale() got an unexpected keyword argument 'bogus' (takes factor, times)` or `pv() takes 2 to 3 argument(s) (cash, periods, spread), got 1`. With a real overload set the generic line is kept, because naming one signature would mean picking an arbitrary member of the set. The error path also got 17% quicker.
- **`generate` now says what it could not bind.** A build that printed `✓ Successfully built` could still be missing names the user wrote, with the only notice being one line of stderr eight lines earlier, or nothing at all. One report after the banner now names them, grouped by reason and capped: enum types, free functions dropped for being overloaded, and free functions that share a name with a function template. The same records reach `--json` as a typed `unbound` field, since `status` was `"ok"` and `errors` was `[]` for all of them.
- **Enums are no longer discovered as classes.** The discovery scan matched the token `class` inside `enum class Side`, so every scoped enum was reported as a class to bind and then skipped at import with a message that never said "enum"; a plain `enum Color` was invisible at every stage. Validated across 620 headers in this repo: 94 names removed, none added, every one of them an enum. Generated stubs also annotate enum members and parameters as `int` instead of naming the C++ enum type, which the module never defines and which made the whole `.pyi` unusable to a type checker. `examples/09-enums` documents what does and does not work rather than promising an API that was never implemented.
- **Two classes with the same unqualified name are caught before codegen.** A module binds every class by its simple name, so `lib::Config` and `lib::detail::Config` made the compiler reject a generated file the CLI then deleted. `generate` now names both declaration sites and explains why `MIRROR_BRIDGE_SKIP` on one does not help.
- **`mirror_bridge diff` refuses to record a baseline that would pass forever.** Headers in subdirectories, or any header containing the text `MIRROR_BRIDGE_SKIP`, could leave the snapshot empty, after which `--check` passed even once every class was deleted. That is now an error (exit 3) naming the cause and pointing at the generated stub as a check that cannot drift. An unknown flag is rejected (exit 1) instead of being taken as the source directory, which is what the scaffolded README's own `diff src/ --module <name>` did. `--help` now states what `diff` does and does not see.
- **Class-typed values are identity-checked at the Lua and JavaScript boundaries too** (#18). Same root cause as the Python fix below: every bound class shares one wrapper layout, and conversion read the held pointer out of whatever object arrived. In Lua the only test was `lua_isuserdata`, so `curve.at(label, 2.0)` returned `4.0513382958982e-322`, a denormal read out of the `std::string`'s bytes; in JavaScript `napi_unwrap` says an object was wrapped but never says wrapped as *what*, so `Curve.prototype.at.call(label, 2.0)`, `curve.blend(label)` and a property accessor lifted off the prototype all did the same. Reachable from ordinary script with no unsafe API, and a plausible wrong number rather than an error. Both backends now refuse, naming the class expected and the class that arrived (`blend: argument 1 expected Curve, got Label`), as a Lua error or a `TypeError`. Covered by `tests/lua/type_safety/` and `tests/js/type_safety/`.
  - The receiver is checked, not just the arguments: `obj.method(x, ...)` in Lua and `Class.prototype.method.call(x, ...)` in JavaScript reach the same code as a normal call with whatever the caller put first as `self`. So do metamethods and accessors pulled off a metatable or prototype.
  - Derived-to-base conversion keeps working and is now offset-adjusted, so `struct Both : First, Second` passed where a `Second` was expected reaches the right subobject instead of returning `First`'s bytes — a silent wrong answer in both backends before. Lua identifies a class by its metatable, which lives in the Lua registry, so a class bound by one `.so` is still recognised in another; the JavaScript backends keep that state per `.node` file, so a *derived* class bound by another module is not convertible there (the exact class still is).
  - **In Lua the identity is a word written inside the wrapper, not the metatable attached to it.** A metatable looks like the natural choice and is not one: `setmetatable({}, getmetatable(curve))` puts a class's metatable on a plain table from ordinary Lua with no privileged library, and `debug.setmetatable` puts it on any value in the process, the standard library's own file handles included. A check on the attached metatable therefore accepted values with no wrapper behind them and read a C++ object address out of them anyway — a null dereference for the table, and for a file handle a read, a write and a `__gc` free at an address the script chose. Lua has no API in the other direction: nothing in the language or the debug library writes a full userdata's payload, so the payload is where the identity belongs, once `lua_touserdata` and `lua_rawlen` have established the value really is a full userdata long enough to hold a wrapper. That is two C API calls and a load where fetching the metatable was four: `c:at(2.0)` 72.1 -> 75.9 ns/call and `c:nullcall()` 60.7 -> 65.1 ns/call (floor of 7 over 2M iterations, 5 interleaved runs). What remains is a foreign full userdata whose first word happens to equal a registered class metatable's address, which a script can neither learn nor write.
  - **`napi_unwrap` says an object was wrapped, never by whom.** The private key it reads belongs to the Node environment rather than to a module, so every other native addon in the process hands its wrapped objects back through it with that addon's own payload layout — and the class tag was read from the front of that payload and followed as a `const char*`. A null or small-integer first word crashed the process; anything else copied a page of the other addon's heap into a catchable `TypeError` message. Each wrapper now leads with a magic word and nothing is read out of a payload that does not carry it. JavaScript stays at parity: the check is a load and a comparison on an unwrap that was already happening. `tests/js/type_safety/foreign_addon.cpp` is a second addon built for the test.
  - **Behaviour change**: script that relied on one bound class silently converting into an unrelated one now gets an error. In Lua a plain table is still accepted where a bound class is expected, which is how nested structs are written from Lua.
  - The V8 backend (`javascript/mirror_bridge_v8.hpp`) got the same gate, built on `FunctionTemplate::HasInstance`, and **nothing in CI verifies it**. The file has not compiled since before this change against the V8 the image actually has — 7.8, from `libnode-dev`, at `/usr/include/node/v8.h` — because it calls `String::NewFromUtf8Literal` and the one-argument `String::NewFromUtf8`, both V8 8.x. The `test-v8` job gates on `/usr/include/v8.h`, which does not exist, so it skips and says the image needs `libv8-dev`; `tests/run_all_tests.sh` gates on the path that does exist, so it has been attempting the V8 build and reporting the failure non-blockingly for longer than this branch. With those two API calls patched locally the backend compiles and runs as a Node addon, which is how the gate was exercised by hand: a receiver of the wrong class is refused, and a `Multi : Pad, Base` passed as a `Base` reaches the right subobject. Two defects found that way and **not** fixed here, both present on `main`: the `Bindable` overload of `from_v8` is declared after `call_method_impl` and `v8_setter` call it, so a bound-class parameter or data member does not compile at all; and `weak_callback` is defined but never installed, so every JS-constructed object leaks its wrapper and its C++ object.
  - `describe_v8_value` was outside the gate it documents: it read the internal field behind only an `InternalFieldCount()` test and followed the result as a `const char*`. Ordinary Node objects carry internal fields — `Buffer`, `MessagePort`, `vm.Script` — so `Base.prototype.get_b.call(new vm.Script('1'))` put raw heap bytes into the `TypeError`'s message, and a wild pointer crashed inside the call. It goes through `HasInstance` like everything else now. The slow-path scan also ignored which isolate a class's template belonged to, which an embedder with two isolates would have read through the wrong one.
- **Class-typed arguments are identity-checked at the Python boundary.** Every bound class shares one wrapper layout, and conversion read the wrapper out of whatever `PyObject` arrived after only a null check, so a wrong type was reinterpreted rather than rejected: passing an `int`, `str`, `dict` or `list` where a bound class was expected **segfaulted the interpreter**, and passing a *different* bound class returned a plausible number computed from that object's bytes. Both now raise `TypeError`. Conversion to a base class is also offset-adjusted, so passing a derived object where a base that is not at offset 0 is expected (`struct Swap : Observable, Priceable`) reaches the right subobject instead of returning garbage. Covered by `tests/type_safety/`.
  - The same gate now also covers the paths that reached around the conversion functions: binary operator slots (`5 + vec` entered the slot with `5` as `self` and segfaulted), the member-template descriptor (`Cls.tmpl.__get__(5)[T]()`), and `mp_subscript`/`tp_call`, which leaked `NotImplemented` to the caller instead of raising. A `shared_ptr`/`unique_ptr` to an abstract pointee reported a successful conversion while leaving the pointer empty, so the callee dereferenced null; it now fails conversion.
  - Classes with a conversion function (`explicit operator double() const`) failed the *entire module build*, because a conversion function is not an operator function and reached `identifier_of`. Same cause, same fix, in `core/mirror_bridge_plan.hpp`: one namespace-scope `operator+` ended the planner's consteval evaluation, which silently cost the module every free function and every template instantiation while still reporting success.
  - **Behaviour change**: code that relied on one bound class silently converting into an unrelated one now raises `TypeError`. Derived-to-base conversions (including virtual and non-first bases), Python subclasses, and the same class bound by two modules all keep working. Not convertible any more: a derived class whose module has not been imported, and a base C++ itself would refuse at that call site (inaccessible, or ambiguous through non-virtual multiple inheritance).
- A `noexcept` free function failed the whole module build instead of being bound: `noexcept` is part of the function type since C++17 and `FunctionTraits` had no specialization for it, so even the "skip what cannot be bound" guard could not fire (it instantiates the traits itself).
- Single-header `mirror_bridge_python.hpp` could not compile standalone: it still `#include`d `python/mirror_bridge_stubgen.hpp`, which the amalgamation never inlined. The stubgen header is now spliced in, `amalgamate.sh` fails if any local include survives, and a new `single_header_standalone` ctest compiles the header with no repo include path (#12).
- `const char*` constructor/method parameters were dereferenced as if they were pointer-holder storage, producing garbage or failing to compile — pointer-typed *values* are now distinguished from pointer-holder storage
- Virtual-override dispatch (`dispatch_python`/`has_python_override`) now acquires the GIL itself, making overridden virtuals safe to call from pure C++ threads that never held the GIL (previously undefined behavior)
- Constructor calls with arguments no constructor accepts now raise `TypeError` instead of silently returning a default-constructed object
- The Python single header shipped raw `#include` lines for `mirror_bridge_annotations.hpp` and `mirror_bridge_eigen.hpp`, so it could not compile standalone; the amalgamation now inlines both at their include site
- `from_python_pointer` accepted `None` as a "successful" null pointer that was then unconditionally dereferenced; `None` now fails conversion (TypeError / next overload)
- `T&` parameters of copyable bound classes mutated a temporary copy, silently dropping the mutation
- CMake helper functions' positional-source parsing leaked `INCLUDE_DIRS` values into the source list
- `mirror_bridge version` claimed Bloomberg clang-p2996 was required; it now reports both supported compilers and which one auto-detection selected

### Notes
- P3394 field annotations (`[[=exclude{}]]`, `[[=readonly{}]]`) are read by the Python backend only. The Lua and JavaScript backends enumerate every named member, so an annotated field is still bound there.
